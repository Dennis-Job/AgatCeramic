# Безопасное логирование и персональные данные

Логи приложения — операционные данные, а не источник для хранения профилей
клиентов. Не записывайте персональные данные или секреты в сообщение лога и
контекст. Вместо этого используйте стабильные идентификаторы и операционные
факты: например, `order_id`, `import_id`, `status` и агрегированные счётчики.

Перед форматированием и записью каждый настроенный канал приложения запускает
`MaskSensitiveLogData`. Процессор заменяет значения чувствительных ключей и
вложенных ключей, включая учётные данные, токены, email, телефоны, имена,
адреса, комментарии, данные карт и cookie. Также он удаляет email-адреса и
номера телефонов из свободного текста сообщения. Для исключений в контексте
сохраняется только имя класса.

Этот процессор — дополнительный защитный барьер, а не разрешение логировать
персональные данные. Новый код обязан изначально избегать PII в сообщениях и
контексте логов. Аварийный logger Laravel, используемый только при ошибке
создания обычного logger, находится вне настроенного pipeline каналов; не
допускайте чувствительных данных и в конфигурации запуска, и в сообщениях
стартовых ошибок.

Описанные меры поддерживают минимизацию данных, но сами по себе не подтверждают соответствие
152-ФЗ. Канонические сроки, основания для согласования, legal hold и требования к уничтожению
зафиксированы в
[`PERSONAL_DATA_LIFECYCLE.md`](PERSONAL_DATA_LIFECYCLE.md). Пока документ имеет статус `proposed`,
его сроки не разрешают необратимую production-очистку.

## Application log retention

Maximum для обычных application/HTTP/queue logs во всех локальных и внешних sinks — 14 дней. PII
запрещена независимо от срока. `stack` по умолчанию использует rotating `daily` channel с
`LOG_DAILY_DAYS=14`; production обязан сохранить эту границу и отдельно подтвердить provider-side
retention/oldest object. `single` остаётся доступен только для осознанной локальной диагностики и не
является допустимой production-конфигурацией.

Retention-команды выводят только batch UUID, scope/action, cutoff и агрегированные counts. При
ошибке в log попадают batch UUID, scope и класс исключения без message, query bindings или PII;
полная техническая видимость сохраняется в append-only `retention_executions`.

## Audit log retention

Записи audit trail, включая разрешённые snapshots участников и объектов, хранятся пять лет.
Ежедневный scheduler запускает `php artisan audit:prune`, который безвозвратно удаляет записи
старше `AUDIT_LOG_RETENTION_YEARS` (по умолчанию `5`). Изменение срока требует отдельного
согласования и новой редакции retention matrix.

В PostgreSQL audit records неизменяемы на уровне БД: прямые `UPDATE` и `DELETE` отклоняются
trigger'ом. Удаление возможно только для `audit:prune` внутри ограниченной transaction-local
настройки и только по сроку хранения.
