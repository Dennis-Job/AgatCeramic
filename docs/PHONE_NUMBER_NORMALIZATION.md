# Единый формат телефонов

Телефоны в `orders.customer_phone`, `contact_requests.phone`, `stores.phone` и
`site_settings.phones` сохраняются и передаются API в формате `+7` и десять цифр
без пробелов: `+79991234567`. В интерфейсах клиента и админки номер отображается
как `+7 (999) 123-45-67`, а `href="tel:..."` использует каноническое значение.

На входе API совместимо принимает канонический номер, формат с пробелами,
скобками/дефисами, десять цифр без кода страны и прежний префикс `8` с десятью
цифрами. Нормализация выполняется общим `RussianPhoneNumber` в Form Requests до
валидации. Неполные номера, иностранный код, буквы, добавочные номера, массив
вместо строки и другие неподдерживаемые значения возвращают `422`.
Необязательные телефоны сохраняют поддержку `null`, а анонимизированные заказы
сохраняют `customer_phone=null`.

Настройки сайта содержат один номер. Для совместимости имя API-поля и JSON-колонка
остаются `phones`: допустимы `[]` или `["+79991234567"]`; новое значение с несколькими
номерами отклоняется. Исторические списки не усекаются автоматически: владелец
должен явно выбрать номер и подтвердить замену при редактировании.

API возвращает канонический формат. Исторические данные до отдельной нормализации
могут оставаться в прежнем виде; интерфейсы умеют форматировать полный старый
номер. Поиск обращений и заказов сохраняет обычный поиск по тексту и дополнительно
находит канонический номер по полному форматированному номеру.

## Проверка существующих данных

Команда по умолчанию ничего не изменяет:

```sh
docker compose exec -T backend php artisan phones:normalize
```

Она выводит только режим, технические table/id, тип проблемы (`invalid`/`multiple`)
и счётчики. Телефоны, имена и другие персональные данные не печатаются. `eligible`
означает количество однозначных преобразований, `changed` — реально выполненных.
Пустые/`null` значения сохраняются. Проблемный номер или список из нескольких
номеров остаётся без изменений; команда возвращает код `1`, пока такие записи
есть, и `0` при их отсутствии. `--apply` не устраняет эти проблемы автоматически.

Перед применением оператор:

1. Создаёт защищённую резервную копию и проверяет восстановление на отдельной базе.
2. Выполняет dry-run, разбирает технические ID проблемных записей под штатными
   правами доступа и согласует исправление неоднозначных данных с владельцем.
3. Проверяет `--apply` на копии и сравнивает счётчики и исходные проблемные значения.
4. Выполняет `php artisan phones:normalize --apply` в согласованное окно и повторяет
   dry-run. Повторный `--apply` идемпотентен: уже канонические номера не меняются.

Сервис обрабатывает записи порциями и блокирует изменяемую строку в транзакции.
Меняется только телефон, исходные `created_at`/`updated_at` сохраняются, поэтому
преобразование не продлевает сроки хранения обращений. Прерывание допускает
безопасный повтор. Никакая migration автоматически не запускает эту команду.
Обратное восстановление исходного форматирования производится из защищённой копии;
само каноническое значение не содержит информации о прежних пробелах и скобках.

## Восстановление и повтор checkout

Retention tombstones проверяют HMAC исходных контактов. При восстановлении старой
копии сначала выполняется штатный replay tombstones, затем нормализация телефонов.
Не переписывать старые backups, tombstones и их HMAC; не применять нормализацию к
восстановленной копии до replay, иначе старый fingerprint перестанет совпадать.

Checkout вычисляет HMAC проверенного тела после нормализации: новые запросы с
форматированным, национальным и каноническим вариантом того же телефона имеют
одинаковый idempotency fingerprint. Активный ключ, созданный прежней версией до
обновления, может иметь HMAC форматированного номера: повтор с таким ключом
в течение прежнего 24-часового срока может вернуть `409`. При выкладке следует
учесть это окно и сначала проверить существующий номер заказа; нельзя автоматически
повторять покупку с новым ключом, поскольку заказ уже мог быть создан.
