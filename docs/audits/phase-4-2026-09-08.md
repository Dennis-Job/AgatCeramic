## Дефекты перед приёмкой

### 1. P1 — импорт групп читает скрытый справочник как строки групп (TASK-058)

`backend/app/Services/ProductGroupImportService.php:218`: проверка пустой строки учитывает весь массив ячеек, включая скрытую колонку Z со списком осей. При числе осей больше числа групп добавляются пустые группы с неизвестным действием, и весь файл отклоняется.

Воспроизведено чтением реально сгенерированного шаблона текущего каталога: получено 28 строк групп; строки 27–29 содержат пустые action/key/source/code/name/axes. Проверка использовала `createTemplate()` и reflection-вызов `read()`, без записей в каталог; временный файл удалён.

Исправление: проверять пустоту только рабочих колонок. Регрессия должна скачивать настоящий шаблон со скрытым справочником и импортировать его после изменения группы, включая случай осей больше, чем групп.

### 2. P1 — отложенная очистка может удалить новое актуальное фото (TASK-056)

`backend/app/Services/ProductImageImportService.php:178–194`, `backend/app/Jobs/DeleteStoredFile.php:38`.

По коду: путь фото повторно используется. Замена JPG → PNG ставит удаление JPG в очередь. Если следующая замена PNG → JPG выполняется раньше этой очистки, старое задание удаляет уже новый JPG. Такое возможно и с одним воркером, когда оба импорта стоят в очереди до добавления заданий очистки. Запись изображения в БД останется, файл исчезнет.

Исправление должно исключить удаление нового поколения файла: например, уникальные пути версий с сохранением пользовательского имени. Нужен тест двух замен с отложенным запуском cleanup. На рабочем каталоге разрушительный сценарий не запускался.

### 3. P1 — ZIP не имеет устойчивого продолжения после остановки (TASK-056)

`backend/app/Services/ProductImageImportService.php:35–37,207–210`; `backend/app/Jobs/ProcessProductImageImport.php:21`; `backend/config/queue.php:71`.

По коду: каждый повтор обходит архив с начала, без сохранённых отметок обработанных SKU. Остановка после первой из двух папок приводит при повторе к повторной замене первой галереи, дублированию аудита и счётчикам 3 обработанных папки из 2. Архив, не укладывающийся в timeout, может так и не обработать последние папки.

Кроме того, timeout задания — 300 секунд, а значение Redis retry_after по умолчанию — 90. При нескольких воркерах возможен повторный захват ещё выполняющегося задания.

Нужны транзакционные checkpoints по SKU, ограниченные порции работы и согласованные timeout/retry_after. Проверить остановку воркера после успешной папки и продолжение без повторов.

### 4. P2 — подготовка импорта цен и групп не атомарна (TASK-057/058)

`backend/app/Services/ProductPriceStatusImportService.php:99–105`: items записываются по одному до сохранения total_rows. Остановка оставляет частичный план при total_rows=0; повтор инициализации упирается в уникальность `(product_import_id,row_number)`.

`backend/app/Services/ProductGroupImportService.php:127–132`: total_rows сохраняется раньше item. Остановка между ними оставляет ненулевой total без плана. `ProcessProductImport.php:82–86` пропускает initialize, и операция может завершиться успешно без применения изменений.

Вывод основан на коде, аварийное завершение рабочих процессов не выполнялось. Нужна транзакционная публикация полного плана с блокировкой и тесты отказа на обеих границах.

### 5. P2 — импорт цен скрывает причину ошибки файла (TASK-057)
