# Производительность поиска и счётчиков товаров — 2026-11-25

Исторический отчёт по TASK-A075. Текущее состояние проекта описано в
[CURRENT_STATE.md](CURRENT_STATE.md), порядок проверок — в [CI.md](CI.md).

## Методика

Замеры выполнены в отдельной PostgreSQL 17.9 с локалью `C.utf8` и PHP 8.3.35.
Исходная версия — `9baa949`. Синтетический каталог содержит 200 000 товаров,
40 категорий, 80 брендов и 3 200 коллекций. Из товаров 126 316 связаны с
коллекциями, 18 181 участвуют в распродаже и 11 764 скрыты. У части товаров
отсутствуют цена, остаток или один из идентификаторов.

Для каждого сценария один вызов прогревает кеш, ещё семь дают медиану суммы
времени SQL-вызовов Laravel. Замер списка включает подсчёт строк и получение
первой страницы из 25 товаров. Пустой список выполняет только подсчёт строк.
Замер счётчиков включает все запросы `ProductQuery::filterCounts`. Время
HTTP-обработки, авторизации, валидации и загрузки связей ресурсов не включено.
Планы `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` сняты отдельно от замеров времени.

## Результаты

Во всех девяти сценариях совпали четыре значения счётчиков, общее число
товаров и идентификаторы первой страницы в исходном порядке. Счётчики выполняют один SQL
вместо четырёх. Активность учитывает выбранную распродажу, распродажа учитывает
выбранную активность. Остальные фильтры применяются ко всем четырём счётчикам.

Повторный замер на новой базе с индексом, созданным до заполнения, дал те же
счётчики, общее число и порядок товаров. Для редкого имени он показал 3,06 мс
на счётчики и 5,33 мс на список.

### Планы PostgreSQL

Для редкого совпадения исходный план списка дважды выполняет `Seq Scan` по
`products` с отдельным подзапросом коллекций. В плане подсчёта строк PostgreSQL
тратит 215,0 мс из 417,7 мс на JIT. Новый план сначала получает ID подходящих
коллекций, затем объединяет в `BitmapOr` триграммные поиски и поиск по
`products_collection_id_brand_id_index`. Для редкого имени список обращается
к 456 буферам вместо 11 516, счётчики — к 228 вместо 23 194. Учитываются
обращения к общим буферам `hit + read` в корневых узлах планов всех запросов
операции.

При двухсимвольном шаблоне `ик` некоррелированный `IN` использует последовательное
сканирование. Пробный `ANY` с GIN затратил 264,46 мс на счётчики и 568,83 мс на
список в медиане трёх запусков. `UNION ALL` по ID дал близкие результаты на редких
совпадениях. На совмещённых фильтрах он занял 209,33 мс для счётчиков и 87,54 мс
для списка. Условие `ANY` позволяет планировщику работать с общими фильтрами в
одной выборке. Для шаблонов без трёх последовательных букв или цифр выбран `IN`.

Пробный B-tree `(created_at, id)` сократил время списка без фильтров до 10,09 мс.
При редком запросе по имени медиана выросла до 111,31 мс, потому что PostgreSQL
выбрал обход по порядку даты с проверкой поискового условия. Миграция включает
только триграммный индекс. Широкие запросы остаются зависимыми от размера каталога.

GIN занимает 79 МиБ при размере таблицы 45 МиБ. Построение через Laravel на
этом каталоге заняло около пяти секунд. Эта операция блокирует запись в
`products` на время построения. Стоимость записи после добавления индекса и
время миграции на рабочем каталоге не измерялись.
[Документация pg_trgm](https://www.postgresql.org/docs/17/pgtrgm.html) ·
[CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html)

## Проверки

- 20 целевых тестов поиска, счётчиков, экспорта и OpenAPI на PostgreSQL.
- Полный набор PostgreSQL Feature в стандартном порядке — 842 теста. Полный
  набор SQLite — 944 теста, включая 8 штатных пропусков.
- В прогоне PostgreSQL с seed `48048` один тест журнала аудита завершился
  ошибкой. Проверка ищет `id` во всём JSON и находит совпадающий `actor.id`.
  Ошибка воспроизведена на исходном `9baa949` с начальными ID 5 для пользователя
  и 3 для первой из трёх записей журнала.
- Миграция прошла `up/down/up` на 200 000 строках. Откат сохранил строки и
  `pg_trgm`, повторное применение восстановило валидный индекс.
- Pint, PHPStan, архитектурная проверка и независимое ревью SQL.

## Воспроизведение

Скрипт [benchmark-product-query.php](../backend/scripts/benchmark-product-query.php)
работает с выделенной локальной `agatceramic_feature_test`. Скопируйте скрипт в
`backend/scripts/` checkout `9baa949` и выполните команды из `backend/` с пустой
базой в [изолированном тестовом окружении](CI.md).

```bash
php scripts/assert-safe-postgres-test-environment.php agatceramic_feature_test
php artisan migrate --force
php scripts/benchmark-product-query.php seed
php scripts/benchmark-product-query.php measure /tmp/product-query-before.json
```

В текущем checkout примените новую миграцию к той же тестовой базе и выполните
`ANALYZE products` в PostgreSQL. Запустите `php scripts/benchmark-product-query.php measure /tmp/product-query-after.json`
из `backend/` на том же каталоге.

JSON содержит SQL, параметры, планы с `BUFFERS`, медианы и результаты. Для
сравнения значений используйте `result` в каждой паре сценария и операции.
Требования к выкладке и откату индекса описаны в [DATABASE.md](DATABASE.md#products).
