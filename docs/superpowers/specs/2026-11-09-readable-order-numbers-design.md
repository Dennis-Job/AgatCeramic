# Короткие номера заказов с ID клиента

Дата: 2026-11-09. Статус: подтверждено владельцем в чате, реализация разрешена.

## Цель и согласованные требования

Клиент должен легко продиктовать менеджеру номер заказа по телефону.
В номере обязательно присутствует постоянный ID клиента. Владелец подтвердил:
одинаковый телефон означает одного клиента, даже если ФИО или email отличаются.
Регистрация и личный кабинет покупателя не добавляются.

## Рассмотренные варианты

- `124-3`: ID клиента и порядковый номер его заказа. Рекомендован как самый короткий.
- `124-5821`: ID клиента и общий порядковый номер заказа магазина. Длиннее по мере роста магазина.

Для реализации предлагается первый вариант: `customer_id-customer_order_sequence`,
без даты, букв и ведущих нулей. Например, `124-1`, `124-2`, `125-1`.

## Поведение

- Используется общая существующая нормализация `RussianPhoneNumber`: форматированный
  номер, национальные десять цифр и номер с `8` приводятся к `+7` и десяти цифрам.
- Уникальный канонический телефон определяет постоянную техническую запись клиента.
  ФИО, email, адрес и комментарий остаются снимком конкретного заказа;
  сведения из другого заказа не подставляются автоматически.
- При первом заказе после обновления создаётся ID клиента и номер с суффиксом `1`.
  Следующий успешно созданный заказ с тем же телефоном получает следующий суффикс.
- Счётчик не сбрасывается по дням или годам. Отмена и возврат не освобождают номер.
- Повтор checkout с тем же ключом идемпотентности возвращает прежний номер и
  не увеличивает счётчик. Неуспешное оформление не расходует суффикс.
- Параллельные оформления одного клиента получают разные суффиксы, но один ID.
  Уникальность закрепляется ограничениями БД, выделение номера — транзакцией.
- Номер одинаков в API, админке, подтверждении оформления и письмах.
  Компоненты интерфейса уже выводят серверный `order_number`; менять их не требуется.

## Совместимость и границы

Существующие номера `AC-YYYYMMDD-XXXXXXXXXX` сохраняются вместе с поиском по ним.
Предложение исполнителя: исторические заказы не перенумеровываются и не связываются
с новой сущностью клиента автоматически; суффикс считает заказы новой системы.
Массовое сопоставление истории не входит в это изменение.

Поля публичного ответа остаются прежними; расширяется допустимый формат
`order_number`. В OpenAPI нужно описать новый и исторический форматы, а для
административных ответов учитывать существующие обезличенные номера `ANON-*`.
Обновляются ADR-012, API.md, DATABASE.md и CURRENT_STATE.md.

## Данные и безопасность

Предложение исполнителя: минимальная таблица клиентов с каноническим телефоном
и счётчиком; nullable связь и суффикс в orders для совместимости с историей.
Новые идентификаторы и суффиксы назначаются только backend; входные значения
`customer_id` и `customer_order_sequence` не принимаются из публичного запроса.
Длина поля номера должна вмещать два bigint и разделитель.

Сопоставление телефона — внутреннее правило группировки, а не проверка владения
телефоном или основание публично раскрывать предыдущие заказы. Новый публичный
маршрут поиска по ID/номеру не создаётся. Последовательные номера намеренно
заменяют непредсказуемые; это изменение фиксируется в ADR.

При обезличивании удаляются ссылка на клиента и суффикс, а номер по-прежнему
заменяется на `ANON-*`. При удалении/обезличивании последнего связанного заказа
удаляется телефон из технической записи клиента. ID и счётчик остаются без
контактов для предотвращения повторного использования номера; новое оформление
после удаления связи с телефоном получает новый ID. Не сохранять телефон или
его постоянный поисковый хеш после окончания срока хранения связанных заказов.
Конкурентные checkout и retention должны сохранять эту гарантию.

## Проверка реализации

1. API-тесты: первый и повторный заказ, эквивалентные написания телефона,
   разные телефоны, изменившиеся ФИО/email, запрет входных служебных полей.
2. Идемпотентность и откат ошибки: номер и счётчик не изменяются при replay
   или неуспехе; письмо содержит тот же номер, который вернул API.
3. PostgreSQL: конкурентный первый заказ и последующие заказы одного клиента,
   уникальные номера, отсутствие дублирующих клиентов.
4. Retention: отвязка обезличенного заказа, сохранение телефона при оставшемся
   связанном заказе, удаление телефона после последнего, новый ID после удаления
   связи и отсутствие повторного использования номеров.
5. Миграции вперёд/назад на тестовой БД, сохранность старых заказов и поиска,
   backend suite, Pint, PHPStan и проверка OpenAPI по скриптам проекта.

При реализации не запускать изменение существующей рабочей БД без предварительной
проверки миграции на тестовой БД. Коммит — только по прямому указанию владельца.
