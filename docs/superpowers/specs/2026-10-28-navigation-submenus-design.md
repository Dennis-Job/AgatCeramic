# Подменю навигации магазина

Дата: 2026-10-28. Статус: согласовано владельцем 2026-10-28.

Реализовано и проверено: [итоговый отчёт](../../NAVIGATION_SUBMENUS_2026-10-28.md).

## Назначение и согласованный выбор

Владелец хочет при создании или редактировании пункта меню в Admin выбирать,
есть ли у него подменю, и задавать состав вложенных ссылок. После сравнения
интерактивных примеров владелец выбрал «Только раскрытие».
У такого родителя название и стрелка — одна кнопка раскрытия, перехода по
родителю нет. Пункты без подменю остаются обычными ссылками.

## Рассмотренные подходы

1. Ссылка со стрелкой: название открывает страницу, отдельная стрелка раскрывает
   список. Даёт прямой переход в раздел, но требует двух разных целей нажатия.
2. Только раскрытие: название со стрелкой целиком раскрывает список. Проще
   управление на телефоне и компьютере; для перехода в общий раздел нужна
   отдельная вложенная ссылка. Владелец выбрал этот вариант.

## Предлагаемый объём

Одна законченная функция затрагивает существующие API, Admin и Client.
Реализуется один уровень вложенности, без автоматической генерации из каталога,
мегаменю, баннеров, третьего уровня и новых страниц управления. Названия и адреса
вводятся вручную. Текущие палитра, типографика и общие UI primitives сохраняются.

## Admin

Место: «Контент → Общее оформление → Шапка и навигация → Навигация».
У каждого родителя — название и переключатель «Есть подменю»:

- выключен: показывается обязательная ссылка родителя;
- включён: поле ссылки родителя заменяется списком вложенных пунктов;
- у вложенного пункта обязательны название и ссылка; есть добавление, удаление
  и перемещение вверх/вниз, как в существующем редакторе;
- порядок родителей редактируется прежними кнопками, группа перемещается целиком;
- для перехода в общий каталог можно вручную добавить первым подпунктом
  «Весь каталог»; приложение не создаёт бизнес-ссылки автоматически;
- новый пункт первоначально обычная ссылка; включение подменю создаёт одну
  пустую строку. Пустую группу сохранить нельзя;
- переключение режима не стирает набранные значения в текущей сессии редактора:
  временно скрытые ссылка/подпункты восстанавливаются при обратном переключении;
  сохраняется только активный режим, о чём есть короткое пояснение рядом с control;
- ошибки сохранения сохраняют введённые данные; права и блокировка controls во
  время сохранения/публикации используют существующий workflow.

Сохранение черновика, сохранённый предпросмотр и отдельная публикация работают
как сейчас. До публикации посетитель видит предыдущее меню.

## Client

На desktop нажатие по названию или стрелке открывает светлый выпадающий список
под пунктом; повторное нажатие закрывает. Hover не требуется. Одновременно открыта
одна группа. Escape, клик вне и переход по ссылке закрывают список. Открытие
поиска или боковой панели и смена маршрута также закрывают desktop-подменю.

В боковом меню тот же пункт — раскрывающаяся группа с вложенными ссылками.
На телефоне используется это же боковое меню. Одновременно открыта одна группа;
по переходу панель закрывается прежним способом. Escape при открытой группе
сначала закрывает группу и возвращает фокус её кнопке, следующий Escape — панель.

Кнопка имеет `aria-expanded` и `aria-controls`; ссылки остаются обычными
индексируемыми ссылками. Tab/Shift+Tab, Enter/Space, видимый focus и доступные
названия обязательны. Закрытые списки исключены из Tab-порядка; обычная навигация
не получает ARIA-роли application menu. При закрытии по Escape фокус возвращается
кнопке; клик вне сохраняет фокус на выбранном пользователем элементе.

Текущая дочерняя ссылка получает `aria-current="page"`; родитель визуально
отражает активный раздел, но не объявляется отдельной текущей страницей.
Поиск по разделам включает обычные ссылки и все дочерние ссылки; название
родителя само по себе не становится результатом без адреса. При совпадении
запроса с названием группы показываются её дочерние ссылки. Если адреса
повторяются, результаты дедуплицируются по адресу с сохранением первого порядка.

Ссылки присутствуют в SSR DOM, даже когда список закрыт. Dropdown не должен
обрезаться существующей ограниченной прокручиваемой desktop-навигацией. Конкретный
способ позиционирования — решение исполнителя с проверкой длинных меню и коротких
viewport. Состояния открыто/закрыто, normal/reduced motion и resize не должны
ломать существующие focus trap, scroll lock, поиск и модальные панели.

## Данные и совместимость

Предложение исполнителя: расширить только `header.navigation` двумя формами:

```json
[
  { "label": "О компании", "to": "/about" },
  {
    "label": "Каталог",
    "children": [
      { "label": "Весь каталог", "to": "/catalog" }
    ]
  }
]
```

Группа определяется наличием `children`; поле `to` у неё не передаётся. Это
исключает сохранение активной ссылки у родителя и дублирование отдельного флага
типа. Старые `{label,to}` продолжают приниматься и выводиться без изменений.
Смешанная форма с `to` и `children`, пустые группы, дополнительные уровни,
неизвестные поля и небезопасные адреса отклоняются сервером.

Предлагаемые ограничения: прежние 1–16 родителей, 1–16 ссылок в группе,
название до 255, URL до 2048 символов. URL — внутренний путь от `/` или HTTPS
по существующему SafeSiteUrl. Порядок определяется массивами. Client также
фильтрует недопустимые ссылки до вывода. Если после фильтрации группа пуста,
она не отображается.

Обновляются все существующие пути записи и чтения общего оформления: основной
site-appearance, совместимый home-page и page site_layout/preview, их типы,
валидация и OpenAPI. Footer сохраняет плоский SiteLink: расширять общий тип
ссылки на все места использования нельзя.

Хранение остаётся в существующем JSON; новые таблицы и миграция старого меню
не требуются. Рабочие записи и опубликованные snapshot автоматически не
переписываются и не публикуются. Существующие разрешения, аудит и transaction
границы сохраняются. API и оба frontend разворачиваются согласованно: старый
Client не умеет выводить новые группы.

## Проверка и приёмка

- Backend: legacy и смешанное меню, все пути записи/чтения, validation 422,
  глубина и лимиты, unsafe URL, черновик/публикация, отсутствие утечки черновика,
  permissions; OpenAPI validation/compatibility, PHP formatting/static analysis.
- Admin: включение/выключение режима без потери текущего ввода, редактирование,
  порядок, удаление, пустые/ошибочные значения, сохранение/повторная загрузка,
  публикация и настоящий Nuxt preview; профильные unit/E2E, lint/format/build.
- Client: desktop и боковое меню, переходы, поиск, текущий раздел, клавиатура,
  Escape/внешний клик, SSR/hydration, overlay-регрессии, reduced motion;
  typecheck/format/build и профильные E2E.
- Визуальная проверка 320/640/768/1024/1280 px, длинных русских названий,
  предельного меню и короткого экрана, отсутствие overflow/обрезания dropdown.
- Независимый UI Design Guard по docs/UI_DESIGN_REVIEW.md до завершения.
- Обновить UI-kit, описание контентного редактора, API-документацию и tasks.
  Проверить diff и список файлов. Коммит — только по отдельному указанию владельца.

## Что оставлено исполнителю

Разделение небольших feature/shared компонентов и composables, локальная модель
редактора для временно скрытых значений и способ безопасного позиционирования
dropdown. Решения должны следовать AGENTS.md обоих frontend и сохранять
утверждённый визуальный стиль. Перечисленные ограничения и один уровень
вложенности являются предложениями исполнителя и входят в согласование документа.
