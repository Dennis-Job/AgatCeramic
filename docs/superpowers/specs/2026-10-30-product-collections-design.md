# Коллекции товаров: справочник, перенос данных и блок карточки

Дата: 2026-10-30. Статус: утверждена владельцем в чате 2026-10-30.

## Основание и согласованные требования

Владелец выбрал отдельный справочник коллекций, связанный с брендами и товарами,
вместо хранения коллекции только в характеристике. Подход подтверждён в чате
2026-10-30. Для коллекции нужны название, описание и фотография; страна берётся
из бренда. Дополнительно согласован необязательный заголовок блока, независимый
от названия коллекции, и настройка использования коллекций в категориях.

Прямое уточнение владельца: если у товара нет коллекции, блок коллекции на
карточке сайта не выводится. Не выводятся также его обёртка и пустой отступ.

Визуальный источник блока — секция `INTERIOR` в `productExample.html` после
характеристик/описания: текст слева, фотография справа, вертикальная компоновка
на узком экране. Демонстрационные тексты, фото и предложение визуализации не
становятся контентом AgatCeramic.

## Подходы

1. **Отдельный справочник — выбран владельцем.** Одна коллекция принадлежит
   одному бренду, объединяет товары, содержит общий управляемый контент.
   Требует новых таблицы/связей, API и обновления существующих потребителей.
2. **Метаданные у строковой характеристики — отклонён.** Меньше начальных
   изменений, но владелец контента и область уникальности по бренду остаются
   неявными; неудобны редактор, переименование и проверка связей.

Существующие migrations не переписываются. Добавляются новые обратимые schema
migrations. Перенос данных выполняется отдельным проверяемым процессом.

## Текущее устройство и границы работ

- У `Brand` уже есть nullable `country_code` и связь с медиатекой.
- У `Product` есть nullable `brand_id`, но нет сущности коллекции.
- `PublicProductDetailResource` извлекает название из `kollektsiya`.
- `PublicCatalogQuery` фильтрует по той же характеристике и бренду.
- Категорийный Excel-импорт читает назначенные категории характеристики;
  общие характеристики могут распространяться на товары группы вариантов.
- В Client есть ссылки на коллекцию и отдельная секция вариантов товара.

Работа разделяется на последовательные проверяемые части одного сценария:
schema/API и безопасный перенос; Admin и назначение товарам; интеграция
импорта/экспорта; публичные данные и блок Client. Реализация завершается после
проверки всех частей. Группы вариантов не превращаются в коллекции.

Не входят: отдельные SEO-страницы коллекций, иерархия коллекций, несколько
коллекций у одного товара, галерея коллекции, AI-контент, изменение палитры,
новый сервис визуализации интерьеров, переделка всего импорта или группировки.

## Модель данных

Новая сущность `ProductCollection` и таблица `product_collections`:

| Поле | Назначение |
| --- | --- |
| `id` | Первичный ключ |
| `brand_id` | Обязательный FK на бренд |
| `name` | Название, до 255 символов |
| `slug` | Стабильный URL-идентификатор; уникальность внутри бренда |
| `headline` | Необязательный заголовок блока, до 255 символов |
| `description` | Обычный текст с переносами, до 10000 символов |
| `image_id` | Nullable FK на изображение в существующей медиатеке |
| `is_active` | Разрешено ли публичное использование коллекции |
| timestamps | Стандартные даты |

`description` и `image_id` допускают пустое значение для перенесённых записей и
постепенного заполнения. Admin явно показывает «Не заполнен блок коллекции»;
не выдаёт такие записи за готовый блок. Для нового справочника не создаются
демонстрационные описания и фото. Публикация самого товара не требует коллекции
или заполненного рекламного блока.

У `products` добавляется nullable `collection_id`. Коллекция товара должна
принадлежать его бренду. Товар без бренда не может иметь коллекцию. Название
коллекции уникально внутри бренда без учёта регистра и крайних пробелов;
одноимённые коллекции разных брендов допустимы. Точные ограничения и индексы
проверяются на PostgreSQL, включая согласованность пары brand/collection.

У `categories` добавляется `uses_collections`, по умолчанию false. Настройка
явная для конкретной категории товара, без неявного наследования. Для
существующих категорий её включение предварительно предлагается в отчёте
переноса, если категории уже назначена характеристика `kollektsiya`.
Категории не распознаются по русскому названию и не хардкодятся во frontend.

Страна не дублируется в коллекции: изменение страны бренда сразу отражается
везде. При незаполненной стране показывается «Не указана» в Admin; в Client
пустая страна скрывается.

## Инварианты и жизненный цикл

- Назначение коллекции допускается только в категории с `uses_collections`.
- Смена бренда или категории не очищает коллекцию молча: сохранение
  несовместимого сочетания возвращает validation error. В форме пользователь
  явно выбирает другую коллекцию или «Без коллекции».
- Отключить `uses_collections` при связанных товарах нельзя до явного снятия
  назначений. Сообщение объясняет причину и количество связей.
- Бренд коллекции с привязанными товарами менять нельзя. Смена имени/контента
  не затрагивает назначения. Slug не меняется автоматически при переименовании.
- Удаление занятой коллекции запрещено, предлагается деактивация. Удаление
  свободной коллекции не удаляет общие медиа; используется существующая
  проверка использования файлов и механизм очистки.
- Удаление бренда с коллекциями запрещено до удаления свободных коллекций или
  явного переноса связей. Это изменение существующего поведения документируется
  и покрывается regression test; удаление бренда без коллекций сохраняется.
- Неактивная коллекция остаётся назначенной в Admin, но не выводится публично.
  Это не выключает сам товар и не меняет цену/остаток.
- Коллекция назначается конкретному товару. Новая связь не становится осью или
  общей характеристикой группы и не распространяется молча на другие товары.
- Все write-paths используют общие application-проверки; HTTP validation не
  заменяет проверку актуальных связей в транзакции. Для конкурентных изменений
  нужен согласованный порядок блокировок и ограничения БД.

## Admin

Раздел «Товары → Коллекции», route `/collections`, общий Seller UI-kit и
существующее право каталога `catalog.manage`, как для брендов и категорий.
Код проверен в `PermissionSeeder` и навигации Admin; отдельного `catalog.view`
сейчас нет. Новые роли и фиктивное read-permission не вводятся. Операции
медиатеки дополнительно соблюдают её существующие permissions.

Список с пагинацией: превью, название, бренд, страна, количество товаров,
состояние и действия. Поиск по названию, фильтры бренда и активности. Состояния:
loading, ошибка с повтором, пустой справочник, пустой результат фильтрации.

Форма: название, бренд, автоматически показанная страна, headline, описание,
изображение и активность. Медиа выбирается или загружается существующими
средствами с соблюдением прав; не создаётся независимый upload-механизм.
Проверка MIME/доступности публичного изображения выполняется сервером.

В редакторе товара коллекция находится рядом с брендом, с поиском только внутри
этого бренда и выбором «Без коллекции». При неподдерживаемой категории поле
скрывается; несовместимое историческое назначение показывается явно для
исправления, а не теряется при сохранении. Неактивная текущая коллекция видна
в форме как неактивная; добавлять её новым товарам нельзя.

Настройка категории находится в существующей форме, не в новой странице.
Для длинного содержимого, 320/640/768/1024/1280 px, клавиатуры, ошибок и
disabled/loading состояний соблюдается `docs/UI_DESIGN_REVIEW.md`.

## API и публичное представление

Admin REST CRUD: `/api/v1/admin/collections`, одиночная запись по ID. Списки
используют существующие data/links/meta. Form Requests, Policy, application
service, Resource; Query при необходимости. Изменения входят в аудит.
Product API расширяется `collection_id`, Category API — `uses_collections`.

Публичное `collection` остаётся nullable и сохраняет `name`/`brand_slug`,
дополняясь ID, slug, headline, description, country_code и безопасным image URL/alt.
Бренд и изображение загружаются заранее, без запросов из Resource.
При отсутствии связи или публично недоступной коллекции возвращается null.

Существующие ссылки `/catalog?brand=...&collection=<name>` продолжают работать
по точному названию в области бренда, но читают новую связь. Неоднозначные
legacy-записи не подмешиваются к другой коллекции. Отдельная смена публичного
URL-контракта в эту задачу не входит. Переименование делает старую ссылку по
названию неактуальной, как и текущая характеристика; стабильные SEO URL — отдельная
задача. Активность коллекции соблюдается при публичной фильтрации.

## Блок карточки Client

Новая секция сразу после вкладок характеристик/описания и до сопутствующих
товаров. Текст слева, фотография справа; бренд/страна в подписи; headline
или название в заголовке; настоящее описание. Ссылка «Товары коллекции» ведёт
в существующий каталог с областью бренда. Услуга «Получить визуализацию» не
добавляется, поскольку её рабочего сценария в задаче нет.

Условия рендера всей секции: есть публичная коллекция, непустое описание и
доступное изображение. Если связи нет, секция отсутствует полностью — прямое
требование владельца. Если метаданные ещё не заполнены после переноса, блок
также скрыт, но существующая текстовая навигация по коллекции может работать.
Пустой headline заменяется реальным названием коллекции.

Нет шаблонной картинки, выдуманного текста или резервного предложения услуги.
SSR и первая hydration-разметка совпадают. Изображение имеет alt, размеры или
aspect-ratio, responsive sizes и отложенную загрузку ниже первого экрана.
Утверждённые цвета и типографика сохраняются. Требование отсутствия секции
заносится в актуальный реестр `docs/CLIENT_UI_KIT.md` вместе с источником и тестом.

## Перенос и совместимость импорта

Сначала read-only preflight: реальные типы/значения `kollektsiya`, бренды,
категории, варианты написания, неизвестные/нестроковые значения. Группировка
только в рамках одного бренда. Нельзя автоматически сливать похожие слова,
разный регистр с разными написаниями или неоднозначные исторические варианты.
Очевидные одинаковые строки объединяются; случаи, требующие решения,
попадают в отчёт с техническими ID и причинами.

Apply — отдельная идемпотентная команда с транзакциями, аудитом технического
контекста и повторной проверкой исходных значений. До apply необходимы backup
и проверка на копии PostgreSQL согласно backend AGENTS. Строки без бренда,
неоднозначные значения и конфликтующие назначения пропускаются с отчётом.
Готовые назначения не перезаписываются. Описания/фото остаются пустыми,
коллекции активны для сохранения навигации; рекламный блок скрыт до заполнения.
Назначения допустимы только после включения подходящих категорий. Предлагаемый
preflight список категорий проверяется перед apply; не включать категории с
неоднозначным назначением автоматически.

`collection_id` становится единственным изменяемым источником коллекции.
Историческая характеристика и значения сохраняются для проверки/отката;
в новых формах и публичных характеристиках нет второго редактируемого поля.
Обычная замена характеристик не должна удалять сохранённые legacy-значения.
Изменение коллекции не синхронизирует исторические строки обратно.
Зарезервированная `kollektsiya` больше не участвует в обязательности,
полноте товара, проверке совместимости смены категории и в осях новых групп.
Иначе новое необязательное поле продолжило бы зависеть от архивной
характеристики. Текущие оси групп с этим slug выводятся отдельным blocker в
preflight, а не переделываются автоматически. Прямая запись legacy-характеристики
через endpoint характеристик возвращает объяснение и предложение использовать
`collection_id`; Excel-alias остаётся отдельной документированной совместимостью.

Переключение чтения — только после успешного переноса, не сразу после schema
migration. Порядок выпуска: preflight на копии → разбор блокирующих случаев →
backup рабочей БД → короткое окно обслуживания с остановкой Admin/import/queue
записей каталога → schema migration и повторный preflight → apply → сверка
покрытия → включение новой версии и возобновление работы. До этого используется
предыдущая версия чтения. Изменение серверного кода и перенос не оставляются
двумя несогласованными работающими версиями.

Критерий переключения: каждое прежнее непустое значение коллекции перенесено
либо включено в явно рассмотренный владельцем список исключений. Неразобранные
неоднозначности, несовместимые категории и группы с legacy-осью блокируют
переключение. Товары без значения коллекции не являются ошибкой. У согласованно
исключённого товара новая связь остаётся null и секция не выводится; исходное
значение остаётся в истории. Проверка покрытия и остановка записей исключают
окно, в котором прежние коллекции пропадут до apply. При неуспешной сверке новая
версия не открывается пользователям; используется проверенный restore/rollback
порядок, без попытки восстановить исходные строки по изменённому справочнику.

Новые Excel-шаблоны и экспорт берут коллекцию из связи, отдельной колонкой
в разрешённых категориях. Старая колонка `attribute.kollektsiya` принимается
как совместимый вход и разрешается по существующей коллекции выбранного бренда;
не создаёт дубликаты и не пишет старую характеристику. Если одновременно
переданы старая и новая колонка, значения должны совпадать либо строка отклоняется.
Пустая ячейка в edit-шаблоне означает явное снятие коллекции; отсутствие колонки
в старом файле сохраняет текущую связь. Неизвестное имя, отсутствие бренда или
неподдерживаемая категория дают понятную ошибку строки. Справочник не создаётся
молча из Excel. Зарезервированная legacy-характеристика исключается из общей
синхронизации характеристик группы; остальные характеристики работают как прежде.

Код поиска, экспорта, клонирования и аудита проверяется на зависимости от
legacy-значения. Клон копирует совместимое назначение новой связи, не получает
его из устаревшей строки. Поиск по названию коллекции использует новый справочник.
Везде, где старое поле продолжает встречаться, его совместимость фиксируется
явно тестом или отчётом; не поддерживаются два конкурирующих источника истины.

## Приёмка и проверки

- CRUD, валидация, отрицательные permissions, журналирование; ограничение
  бренда/категории и удалений, конкурентные изменения связей.
- PostgreSQL: schema up/down на изолированной БД, constraints/indexes,
  preflight/apply/reapply, пропуск неоднозначностей и отсутствие потери данных.
- Коллекции с одинаковым именем у разных брендов разделены.
- API/OpenAPI описывают новые ресурсы и nullable collection; публичные поля
  не выдают внутреннее состояние и закрытые media.
- Excel create/edit/export, старый alias, конфликт двух колонок, пустая ячейка,
  отсутствие колонки, группы вариантов, клонирование и поиск.
- Admin: список, фильтры, редактор, медиа, назначение и очистка; пять ширин,
  клавиатура и доступность, обязательные lint/format/build/unit и релевантные E2E.
- Client SSR/E2E: готовая коллекция; отсутствующая связь; неполные данные;
  неактивная коллекция; смена товара без сохранения чужого блока; реальные ссылки;
  отсутствие пустого места; мобильный порядок и неизменность остальных секций.
- Backend: обязательные проверки из `backend/AGENTS.md`; миграции и SQL на
  PostgreSQL, а не только SQLite. Результаты и ограничения фиксируются честно.
- До сдачи независимый UI Design Guard проверяет Admin и Client; blocking
  findings устраняются с сохранением утверждённой палитры.
- Обновляются canonical API docs/OpenAPI, документация и task status, затем
  проверяются diff/список файлов. Commit только по прямому указанию владельца.

## Решения исполнителя, предлагаемые на утверждение

Категории настраиваются явно без наследования; незаполненный блок скрывается;
заполненность описания/фото не блокирует товар; занятая коллекция и бренд с
коллекциями защищены от удаления; существующие права каталога переиспользуются;
перенесённые коллекции без контента сохраняют текстовую навигацию; старые
значения сохраняются только как история, а Excel получает совместимый alias.

После утверждения этой спецификации составляется план реализации с точными
файлами и проверками. Изменение продуктового кода до утверждения не выполняется.
