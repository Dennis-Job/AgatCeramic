# Самостоятельный каталог товаров — TASK-120

Дата: 2026-11-11. Статус: согласовано владельцем, реализация разрешена.

## Задача владельца

`/catalog` становится полноценным каталогом магазина с боковыми фильтрами.
Наличие товаров и возможность поиска не должны зависеть от добавления блока
«Каталог» в конструкторе страниц. Назначение этого блока будет определено
отдельно. Владелец выбрал полный набор фильтров, включая характеристики.
Порядок категорий должен управляться из админки.
Уточнение владельца: участвуют только характеристики с включённым при их
создании/редактировании признаком фильтрации и только в категориях,
которым они явно назначены.

## Что существует сейчас

- `/catalog` использует `ContentPageView`: нужны опубликованная CMS-страница
  и включённый блок `catalog`, который создаёт `CatalogListing`.
- `GET /api/v1/catalog` уже отдаёт реальные товары, пагинацию и категории;
  поддерживает точные `category`, `brand`, `collection`.
- Категории имеют `parent_id`, `sort_order`, `is_active`. Поле «Порядок
  сортировки» уже редактируется в админке. Характеристики имеют
  `is_filterable`, тип, варианты и назначения категориям.
- Панель «Контент → Общее оформление → Вид фильтров» пока информационная.
  Карточки товаров, вступительный баннер и drawer уже имеют общую реализацию.

## Подход

Развивать действующий Laravel API и выделить feature каталога в Nuxt.
Это предложенный и рекомендуемый технический выбор исполнителя: сохраняется
один источник товаров, цен, остатков и справочников.

Переносить каталог в новый тип CMS-блока противоречит требованию независимости.
Вводить отдельный поисковый движок сейчас неоправданно: для текущей задачи
достаточно серверных запросов к существующим данным.

## Страница и взаимодействие

- Общий `PageIntro` с H1 «Каталог», ниже рабочая область без повторного крупного
  заголовка «Каталог». Палитра, шрифт и карточки сохраняются по CLIENT_UI_KIT.
- На широком экране слева панель около 260 px, справа счётчик результатов,
  сортировка, сетка существующих `ProductCardList` и пагинация по 24 товара.
- На узком экране фильтры открываются кнопкой в общем `UiDialog` drawer.
  Одна реализация формы используется в боковой панели и drawer.
  Порог переключения подбирает исполнитель по доступной ширине карточек.
- Фильтры применяются кнопкой «Показать товары»; изменения до применения
  остаются черновиком формы. Применение закрывает мобильную панель.
  Сортировка и переходы по категориям действуют сразу.
- Применённые ограничения видны над результатами; каждое можно удалить.
  «Сбросить всё» убирает фильтры; сортировка сохраняется.
- Состояние хранится в query URL; reload, ссылка, Назад/Вперёд восстанавливают
  выбор. Изменение фильтров/сортировки переводит на первую страницу.
- Есть состояния загрузки, ошибки с повтором, пустого каталога и отсутствия
  совпадений с предложением сброса. Устаревший сетевой ответ не заменяет новый.

## Категории и управление из админки

- Дерево активных категорий берётся из товарного справочника; порядок братьев:
  `sort_order`, затем название и ID. Меньшее число показывается раньше.
  Не вводить второй порядок категорий в CMS-блоке или оформлении.
- При выборе родителя новый каталог включает товары активных подкатегорий.
  Существующее точное поведение API для старых потребителей сохраняется:
  обход потомков включается отдельным параметром нового интерфейса.
- Не менять существующее правило публикации товаров: активный товар и его
  собственная активная категория. Неактивный предок не скрывает автоматически
  товар активного потомка; в навигации потомок остаётся доступен.
- В админке пояснить назначение существующего поля порядка. Перетаскивание
  категорий не требуется; данные и права `catalog.manage` сохраняются.

## Полный набор фильтров

- Категория, бренд, коллекция выбранного бренда, цена от/до, «В наличии».
  Смена бренда сбрасывает коллекцию. Ссылки из карточек brand/collection
  продолжают работать с существующими параметрами.
- Характеристики подбираются динамически по двум обязательным условиям:
  `is_filterable = true` в справочнике характеристик и явное назначение
  именно выбранной категории. Наличие значения у товара само по себе
  не делает характеристику доступной для фильтрации.
  Нет наследования от родителя, объединения с характеристиками потомков
  или соседних категорий. Если характеристика назначена нескольким категориям,
  она доступна отдельно в каждой из них. Без выбранной категории показываются
  только общие фильтры (бренд, коллекция, цена, наличие), без характеристик.
  Устаревший атрибут коллекции не дублирует коллекции.
- `select` и `multiselect` — выбор нескольких вариантов; boolean — Да/Нет;
  integer/decimal — диапазон; date — диапазон дат; string/text — поиск
  по значению характеристики. Названия, подписи вариантов и единицы — из API.
- Между разными фильтрами действует AND; несколько вариантов одной
  характеристики объединяются OR, в том числе для массивного значения товара.
  Пустое значение не совпадает с выбранным значением; boolean false не теряется.
- При смене категории несовместимые характеристики сбрасываются. Неизвестные
  и недоступные значения в прямой ссылке не расширяют выдачу молча: показать
  понятную ошибку/отсутствие совпадений с возможностью сброса.
  Backend самостоятельно проверяет `is_filterable` и назначение выбранной
  категории; передача характеристики другой категории через URL отклоняется.
- Списки вариантов строятся сервером по публичным товарам выбранного раздела,
  а не по текущей странице из 24 товаров. Прочие выбранные фильтры не убирают
  соседние варианты; выбранные значения остаются доступными для отмены.
  Не загружать весь каталог в браузер или Eloquent-коллекцию ради фильтрации.
- Цена означает цену за указанную у товара единицу продажи. Без цены товар
  виден в обычном списке с «Цена по запросу» и исключается при ценовом диапазоне.
- Сортировки: название А–Я / Я–А, цена по возрастанию / убыванию, сначала новые.
  По умолчанию сохранить название А–Я; товары без цены при сортировке по цене
  всегда в конце, дополнительный порядок по ID обеспечивает стабильность.

## Независимость от конструктора

- Товары и фильтры `/catalog` загружаются независимо от CMS-запроса,
  публикации страницы и наличия любых блоков.
- Опубликованные название, вступительное изображение и SEO страницы `catalog`
  можно использовать как необязательные редакционные настройки; при их
  отсутствии/ошибке работают стандартные значения и баннер.
- Контентные блоки этой CMS-страницы не определяют состав `/catalog` и не
  выводят вторую товарную сетку. Сохранённые блоки не удаляются из БД.
  Админка объясняет эту границу при редактировании страницы каталога.
- `/preview/catalog` показывает ту же самостоятельную страницу с сохранёнными
  черновыми настройками заголовка/баннера/SEO; существующая проверка доступа,
  no-store/noindex и отсутствие черновика в SSR сохраняются.
- Блок `catalog` на других CMS-страницах и его существующий renderer сохраняют
  текущее поведение. Новую функциональность этого блока не придумывать.
- «Вид фильтров» объясняет источники состава и порядка и даёт переходы к
  соответствующим справочникам. Новые переключатели визуального оформления
  не входят в этот объём: внешний вид сохраняет утверждённый UI-kit.

## Реализация и границы

- Тонкий route, feature-компоненты каталога, composable URL/формы,
  типизированный service. Переиспользовать карточки, поля, кнопки, PageState,
  UiDialog, UiCloseButton и токены; новые общие controls документировать.
- Backend: Form Request → Controller → Query → API Resources.
  Отдельная выдача metadata фильтров или opt-in metadata в существующем
  endpoint — решение исполнителя; старый формат и параметры остаются рабочими.
- Типизированная серверная валидация, пределы числа фильтров/значений/длины,
  разрешённые сортировки и параметризованные запросы обязательны. Фильтровать
  и считать результаты в БД до пагинации, учитывать JSON-типы PostgreSQL.
- Не выдавать точные остатки, private media, служебные SKU и закрытые данные.
  Миграции нужны только при выявленной необходимости индексов; не мигрировать
  и не переписывать контент владельца без необходимости.
- SSR включает товары, навигацию, H1, canonical, CollectionPage JSON-LD.
  Базовый каталог индексируемый, если владелец явно не выключил индексацию
  в опубликованных настройках страницы (`is_indexable: false` сохраняется).
  Выдачи с фильтрами/нестандартной сортировкой
  и последующими страницами — `noindex,follow`, canonical на `/catalog`.
  Ошибка основного товарного API даёт 503 и `noindex` при SSR.
- Не включать новые SEO-маршруты категорий/брендов, отдельный search engine,
  изменение карточки товара или новые возможности CMS-блока.

## Приёмка

1. Без блока `catalog`, без опубликованной CMS-страницы и при ошибке CMS
   самостоятельный каталог продолжает показывать товары и фильтры.
2. Изменение порядка категорий в админке отражается на сайте. Проверить
   дерево, родителя/потомков и ссылку на категорию из карточки товара.
3. Комбинации всех типов фильтров, false/0, коллекции разных брендов,
   неизвестные значения, цена без копеек/с копейками, null price, пагинация,
   стабильная сортировка, пустая выдача и восстановление URL покрыты тестами.
   Отдельно проверить отсутствие неназначенных/нефильтруемых характеристик,
   отсутствие наследования между категориями, отсутствие характеристик без
   выбранной категории и отклонение чужих характеристик в прямом API-запросе.
4. Обновить API.md/OpenAPI и проверить контракт; backend feature-тесты,
   форматирование и static analysis по действующим скриптам. JSON-фильтры
   проверить на SQLite и PostgreSQL; недоступную проверку явно указать.
5. Client typecheck/build/format, релевантные Playwright-тесты; Admin checks
   по объёму изменений. Отдельно регрессии CMS-блока, preview и переходов
   brand/collection из товара.
6. Реальные маршруты на 320/640/768/1024/1280 px, SSR/hydration, клавиатура,
   Escape/возврат фокуса, reduced motion, отсутствие overflow, axe.
   Независимый UI Design Guard обязателен до сдачи интерфейса.
7. Обновить CLIENT_UI_KIT, документацию границ CMS и статус TASK-120,
   оставив отдельным открытым подпунктом будущие редактируемые параметры
   представления фильтров. Проверить git diff. Коммиты — только по отдельному
   указанию владельца.
