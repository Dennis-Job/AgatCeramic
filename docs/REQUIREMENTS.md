# Требования AgatCeramic

## 1. Бизнес

AgatCeramic продает:
- керамическую плитку;
- мозаику;
- керамогранит;
- клей;
- затирки;
- сопутствующие материалы;
- сантехнику.

## 2. Клиент

Регистрация не требуется.

Минимальные данные заказа:
- ФИО;
- телефон;
- email, если нужен для отправки подтверждения;
- адрес доставки;
- комментарий;
- состав заказа.

Нужно предусмотреть валидацию и защиту от спама/ботов.

## 3. Заказы

Заказ должен иметь:
- уникальный номер;
- дату/время создания;
- контактные данные;
- адрес;
- состав;
- количество;
- цену на момент заказа;
- итоговую сумму;
- статус обработки;
- статус оплаты;
- дату оплаты, если оплата произошла вне сайта;
- дату передачи менеджеру;
- дату завершения;
- комментарии менеджеров;
- историю изменений.

ВАЖНО: дата создания заказа и дата оплаты — разные даты.

Аналитика должна учитывать продажи по фактической дате поступления оплаты, а не только по `created_at`.

Пример:
заказ создан 31 января, оплачен 2 февраля.
- январь: созданный заказ;
- февраль: реализованная/оплаченная продажа.

## 4. Статусы

Статусы заказа должны быть управляемыми, а не жестко зашитыми во frontend.

Базовый набор:
- новый;
- в обработке;
- ожидает уточнения;
- подтвержден;
- ожидает оплаты;
- оплачен;
- комплектация;
- передан в доставку;
- завершен;
- отменен.

Дополнительно нужен отдельный payment status:
- not_paid;
- pending;
- paid;
- refunded;
- partially_paid.

## 5. Каталог

Нужны:
- категории;
- вложенные подкатегории;
- перемещение категорий;
- SEO-поля категории;
- характеристики категории;
- группы характеристик;
- бренды;
- логотипы брендов;
- товары;
- группы вариаций самостоятельных товаров;
- изображения;
- документы/файлы при необходимости;
- цены;
- остатки;
- единицы измерения;
- артикулы;
- SKU;
- штрихкоды;
- связанные товары;
- рекомендуемые товары.

Для плитки и керамогранита предусмотреть отраслевые атрибуты, например:
- коллекция;
- размер;
- толщина;
- поверхность;
- цвет;
- формат;
- материал;
- назначение;
- класс износостойкости;
- морозостойкость;
- страна производителя;
- количество в упаковке;
- площадь упаковки;
- вес упаковки.

Это не означает, что все характеристики должны быть жестко зашиты. Нужна динамическая система атрибутов.

## 6. Самостоятельные товары и группы вариаций

Каждая продаваемая позиция является самостоятельным товаром. Product владеет собственной карточкой,
SKU, артикулом, штрихкодом, единицей продажи, ценой, остатком, характеристиками и изображениями.
Вложенная продаваемая сущность variant в целевой модели отсутствует.

Товары одной модели можно объединить в группу вариаций. Группа содержит уникальный служебный код,
название, не менее двух товаров и одну или несколько характеристик-осей, по которым участники
различаются, например цвет, формат или поверхность. Осями могут быть скалярные характеристики;
`text` и `multiselect` использовать как оси нельзя.

Все товары группы должны относиться к одной категории и одному бренду, иметь одинаковые значения
всех неосевых характеристик и уникальную комбинацию значений осей. Группа влияет на навигацию между
самостоятельными товарами, но не переносит между ними изображения, идентификаторы, цены или остатки.
Связанные и рекомендуемые товары являются отдельным механизмом и не заменяют группу вариаций.

Обязательность характеристики задаётся при её назначении конкретной категории, а не в глобальном
справочнике характеристик. Неполный товар разрешено сохранить как неактивный черновик; активация
разрешена только после заполнения всех обязательных характеристик категории и остальных обязательных
полей продаваемого товара.

## 7. Массовая работа

Администратор должен:
- импортировать товары из Excel;
- экспортировать товары;
- массово изменять товары;
- массово изменять цены;
- массово изменять остатки;
- массово менять категории;
- массово назначать характеристики;
- видеть ошибки импорта построчно;
- получать результат импорта;
- запускать большие операции через queue.

Нельзя выполнять тяжелый импорт синхронно в HTTP request.

## 8. Бренды

CRUD:
- название;
- slug;
- описание;
- логотип;
- SEO title;
- SEO description;
- активность.

Логотип бренда и связанные с брендом документы/файлы относятся к Media Library
(`TASK-096`, Phase 7). Каталог хранит только управляемые ссылки на media entities и не реализует
отдельное неуправляемое файловое хранилище. SEO title и SEO description относятся к единому
SEO-слою (`TASK-100`, Phase 8), а не к колонкам таблицы брендов.

## 9. Категории

CRUD:
- название;
- slug;
- родитель;
- описание;
- изображение;
- SEO;
- сортировка;
- активность.

Категории могут иметь неограниченную вложенность, если это не создаёт проблем с UX.

Изображение категории относится к Media Library (`TASK-096`, Phase 7). SEO категории относится к
единому SEO-слою (`TASK-100`, Phase 8), а не к колонкам таблицы категорий.

## 10. Характеристики

Нужно управлять:
- характеристиками;
- группами характеристик;
- типом значения;
- допустимыми значениями;
- единицей измерения;
- обязательностью;
- фильтрацией;
- отображением на странице товара;
- сортировкой.

Поддержать типы:
- string;
- text;
- integer;
- decimal;
- boolean;
- select;
- multiselect;
- date;
- range при необходимости.

Цветовые характеристики создаются с типом `select`: `label` опции хранит человекочитаемое название
цвета, а `value` — стабильный код, который может быть HEX-значением (например, `#A1B2C3`). Отдельный
тип `color` не используется.

## 11. Обращения

Нужен раздел обращений:
- обратный звонок;
- запрос ответа по email;
- обращение клиента;
- обращение партнера.

У обращения:
- тип;
- контакт;
- сообщение;
- дата;
- источник;
- статус;
- ответственный;
- комментарии;
- история обработки.

## 12. Контент сайта

Из админки управляются:
- телефон;
- основная email;
- реквизиты ИП;
- логотип;
- социальные сети;
- баннеры;
- главная карусель;
- информационные карусели;
- страницы;
- тексты;
- изображения;
- адреса магазинов;
- часы работы.

Нужен media management.

## 13. SEO

Управление:
- title;
- meta description;
- canonical;
- robots;
- OG title;
- OG description;
- OG image;
- slug;
- structured data;
- sitemap;
- redirects.

Для товаров, категорий и брендов SEO должно быть отдельным управляемым слоем.

### 13.1. Трассировка отложенных требований каталога

| Требование каталога | Владелец реализации | Граница ответственности |
| --- | --- | --- |
| Изображение категории | `TASK-096` Media library, Phase 7 | Catalog предоставляет сущность категории; Media управляет файлом, метаданными, ссылкой и жизненным циклом. |
| Логотип бренда | `TASK-096` Media library, Phase 7 | Catalog предоставляет сущность бренда; Media управляет файлом, метаданными, ссылкой и жизненным циклом. |
| Документы/файлы бренда и каталога | `TASK-096` Media library, Phase 7 | Многоразовые вложения реализуются через Media, без путей к файлам в Catalog API. |
| Title, meta description, OG title и OG description товаров, категорий и брендов | `TASK-100` SEO metadata, Phase 8 | Метаданные хранятся в отдельном SEO-слое и не дублируются в Catalog-таблицах. |
| OG image товаров, категорий и брендов | `TASK-100` + `TASK-096` | SEO хранит назначение OG image, Media управляет файлом и его жизненным циклом. |
| Canonical | `TASK-101`, Phase 8 | Canonical управляется для индексируемых сущностей, включая товары, категории и бренды. |
| Sitemap | `TASK-102`, Phase 8 | Sitemap включает подходящие индексируемые Catalog-сущности. |
| Robots | `TASK-103`, Phase 8 | Управляются entity-level directives и поведение robots.txt. |
| Redirects | `TASK-104`, Phase 8 | Включает редиректы, необходимые при изменении Catalog slug. |
| Structured data | `TASK-105`, Phase 8 | Schema.org формируется для поддерживаемых Catalog-сущностей. |
| SEO AI | `TASK-106`, Phase 8 | AI создаёт только черновики внутри управляемого SEO workflow. |
| Slug | Catalog (`TASK-030`, `TASK-035`, `TASK-036`) | Slug остаётся маршрутизационным полем сущности; SEO-слой его не дублирует. |

## 14. SEO AI

AI должен помогать:
- создавать варианты title;
- создавать description;
- улучшать тексты;
- генерировать alt;
- выявлять дубли;
- предлагать ключевые запросы;
- проверять SEO-поля;
- создавать черновики.

AI-результат сначала должен попадать в draft/preview, а не автоматически публиковаться без предусмотренного workflow.

## 15. Аналитика

Dashboard должен показывать:
- заказы за день/неделю/месяц;
- продажи;
- оплаченные заказы;
- отмены;
- средний чек;
- количество заказов;
- динамику продаж;
- продажи по категориям;
- продажи по брендам;
- продажи по товарам;
- продажи по месяцам.

Отдельно учитывать:
- created_at;
- paid_at;
- completed_at.

## 16. Администраторы

CRUD:
- имя;
- email;
- статус;
- роль;
- permissions;
- последний вход.

Рекомендуемые роли:
- Super Admin;
- Administrator;
- Catalog Manager;
- Order Manager;
- Content Manager;
- SEO Manager;
- Analyst.

Права должны быть granular.

## 17. Безопасность

Нужно предусмотреть:
- authentication;
- authorization;
- rate limiting;
- CSRF/SPA security в выбранной auth-схеме;
- validation;
- audit log;
- безопасную загрузку файлов;
- ограничения MIME/размера;
- отсутствие исполнения загруженных файлов;
- секреты только через environment/secret storage;
- отсутствие PII в логах.

## 18. Что пока НЕ входит

Не включать без отдельной задачи:
- онлайн-оплату;
- клиентскую регистрацию;
- клиентский личный кабинет;
- программу лояльности;
- marketplace integrations;
- мобильные приложения.
