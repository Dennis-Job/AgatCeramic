# AGENTS.md — AgatCeramic

## 1. Назначение проекта

AgatCeramic — интернет-магазин керамической плитки, мозаики, керамогранита, сопутствующих товаров (клей, затирки и т. п.) и сантехники.

Проект состоит из:
- `backend/` — Laravel API-only backend;
- `frontend/admin/` — административная PIM/CRM-панель на Vue.js;
- `frontend/client/` — клиентский интернет-магазин на Nuxt.js.

Backend не должен содержать Blade/HTML-визуализацию. Laravel используется как API-приложение.

## 2. Главные архитектурные принципы

Обязательно соблюдать:
- SOLID;
- REST;
- CRUD;
- DRY;
- KISS;
- разделение ответственности;
- явные границы модулей;
- тестируемость;
- безопасность по принципу least privilege.

Не смешивать:
- HTTP-логику;
- бизнес-логику;
- доступ к данным;
- интеграционную логику.

Предпочтительный поток backend:
HTTP Request -> Form Request -> Controller -> Service/Use Case -> Repository/Query -> Model/DB -> API Resource.

Контроллеры должны оставаться тонкими.

## 3. Backend

Стек:
- Laravel;
- PHP;
- PostgreSQL;
- Redis при необходимости;
- Laravel Queue;
- Laravel Scheduler;
- API Resources;
- Sanctum для админской SPA-аутентификации, если архитектура размещения требует cookie/session SPA auth;
- OpenAPI для API-контракта.

Laravel backend — только API.

Запрещено:
- Blade для интерфейса магазина;
- серверный рендеринг клиентского магазина внутри Laravel;
- бизнес-логику в Eloquent Model;
- SQL-запросы непосредственно в Controller;
- возврат Eloquent Model напрямую из публичного API, если для этого можно использовать API Resource;
- изменение API-контракта без обновления документации.

## 4. Frontend Admin

`frontend/admin/`:
- Vue 3;
- TypeScript;
- Vite;
- Vue Router;
- Pinia;
- Tailwind CSS;
- UI/визуальная основа — TailAdmin Vue.

Админка должна быть SPA.

Визуальный стиль должен соответствовать TailAdmin Vue, но бизнес-функциональность AgatCeramic является собственной.

Основные области:
- Dashboard;
- товары;
- массовый импорт/экспорт;
- массовое редактирование;
- категории;
- характеристики;
- бренды;
- заказы;
- обращения/звонки/email;
- продажи и аналитика;
- пользователи админки;
- роли и права;
- контент;
- SEO;
- настройки сайта;
- магазины/адреса/часы работы;
- медиа.

## 5. Frontend Client

`frontend/client/`:
- Nuxt.js;
- TypeScript;
- SSR/гибридный rendering там, где это полезно;
- SEO-first архитектура;
- структурированные данные Schema.org;
- sitemap.xml;
- robots.txt;
- canonical;
- Open Graph;
- динамические title/description;
- ЧПУ;
- SEO-страницы категорий и товаров;
- оптимизация Core Web Vitals.

Клиентская регистрация НЕ нужна.

Клиент:
1. просматривает каталог;
2. выбирает товар;
3. добавляет его в корзину;
4. оформляет заказ;
5. указывает ФИО, телефон, адрес доставки, комментарий;
6. получает email с номером заказа и информацией по заказу.

Онлайн-оплаты на сайте нет.

## 6. Админская аутентификация

Только администраторы/сотрудники имеют учетные записи.

Должны поддерживаться:
- аутентификация;
- роли;
- permissions;
- блокировка пользователя;
- сброс пароля;
- журнал действий;
- принцип least privilege.

Роли не должны быть захардкожены в frontend.

## 7. Персональные данные

Персональные данные клиентов должны обрабатываться с учетом требований 152-ФЗ РФ.

В архитектуре предусмотреть:
- минимизацию собираемых данных;
- разграничение доступа;
- шифрование чувствительных данных там, где это предусмотрено моделью угроз;
- TLS при передаче;
- безопасное хранение секретов;
- аудит доступа к чувствительным данным;
- политики хранения и удаления;
- отсутствие PII в обычных application logs;
- маскирование PII в логах и аналитике;
- резервное копирование с соответствующим контролем доступа.

Юридическую применимость конкретных мер и документов необходимо отдельно проверить с ответственным за обработку персональных данных/юристом. Не считать наличие encryption само по себе доказательством полного соответствия 152-ФЗ.

## 8. Работа с задачами

Перед началом:
1. Прочитать этот файл.
2. Прочитать релевантные документы в `docs/`.
3. Найти задачу в `tasks/`.
4. Изучить существующий код.
5. Составить краткий план.
6. Не менять несвязанные части проекта.

После реализации:
1. Запустить релевантные тесты.
2. Проверить форматирование/lint/static analysis.
3. Проверить миграции.
4. Проверить API-контракт.
5. Обновить документацию.
6. Обновить статус задачи.
7. Перечислить измененные файлы и результаты проверки.

## 9. Контроль объема задачи

Одна задача должна реализовывать один законченный логический кусок.

Если задача начинает требовать изменения большого количества несвязанных модулей:
- остановиться;
- объяснить проблему;
- предложить разделить задачу.

Не реализовывать дополнительные функции "заодно".

## 10. Git

Перед работой проверить состояние Git.

После работы:
- проверить `git diff`;
- проверить список измененных файлов;
- не удалять существующий функционал без явного указания;
- не делать destructive операции без явного разрешения;
- commit создавать только по явному указанию пользователя.

## 11. Качество

Для каждого нового бизнес-модуля по возможности создавать:
- migration;
- model;
- factory;
- seed при необходимости;
- request validation;
- service/use case;
- repository/query layer при необходимости;
- policy/permission;
- API Resource;
- controller;
- route;
- tests;
- OpenAPI/API documentation.

Не создавать слои только ради слоев: архитектура должна оставаться оправданной.

## 12. AI

AI-функции должны быть изолированы от основной бизнес-логики.

AI не должен:
- напрямую изменять БД без контролируемого application layer;
- обходить permissions;
- публиковать контент без предусмотренного workflow;
- отправлять чувствительные данные внешнему AI-провайдеру без отдельного решения.

AI-функции планируются отдельно.

## 13. Что делать при неоднозначности

Если требование неоднозначно и влияет на архитектуру, безопасность, данные или API:
- не угадывать;
- зафиксировать предположение;
- предложить варианты;
- остановиться перед необратимым решением.

Если деталь несущественна, использовать наиболее простое решение и отметить его в результате.
