# AgatCeramic Client Architecture

Этот файл действует для всего `frontend/client/` и дополняет корневой
[`AGENTS.md`](../../AGENTS.md). Для клиентского Nuxt-кода это главный источник
архитектурных правил. Визуальный контракт описан в
[`docs/CLIENT_UI_KIT.md`](../../docs/CLIENT_UI_KIT.md), порядок приёмки UI — в
[`docs/UI_DESIGN_REVIEW.md`](../../docs/UI_DESIGN_REVIEW.md).

## Цель и источники истины

Клиент — публичный магазин AgatCeramic на Nuxt 4, Vue 3 и TypeScript. Он
использует SSR для индексируемых страниц, Laravel API как источник товарных,
ценовых и заказных данных и не требует учётной записи покупателя.

Приоритет для клиентского кода:

1. Бизнес-требования и безопасность: корневой `AGENTS.md`, актуальные
   `docs/REQUIREMENTS.md`, `docs/API.md` и `docs/openapi.json`.
2. Архитектура Nuxt: этот файл и официальная документация для установленной
   major-версии Nuxt.
3. Визуальный стиль: `docs/CLIENT_UI_KIT.md`, затем предоставленный пользователем
   [`exampleSite.html`](../../exampleSite.html) для деталей уже описанных паттернов.

Для Nuxt 4 сверяться с официальными разделами
[Directory Structure](https://nuxt.com/docs/4.x/directory-structure),
[Data Fetching](https://nuxt.com/docs/4.x/getting-started/data-fetching),
[State Management](https://nuxt.com/docs/4.x/getting-started/state-management) и
[SEO and Meta](https://nuxt.com/docs/4.x/getting-started/seo-meta).

HTML-образец — **визуальный референс**, а не код для переноса, API-контракт,
контент-план или разрешение менять бренд. Надписи PIETRA, контакты, цены,
обещания, отзывы, изображения с внешнего хоста и имитации checkout/подписки
не являются данными AgatCeramic. Не публиковать их без отдельного подтверждения
реального источника. Если пример противоречит требованиям, доступности или
безопасности, сохранить визуальный язык и реализовать корректное поведение.

## Архитектура и направление зависимостей

Соблюдать SOLID, DRY, KISS и разделение ответственности без слоёв ради слоёв:

```text
app/pages -> app/features -> app/components/ui + app/components/shared
                         -> app/composables -> app/services -> Laravel API
app/layouts -> app/components/shared -> app/components/ui -> design tokens
```

- `app/pages/` — тонкие route-level композиции: параметры URL, page-level
  загрузка, SEO и сборка секций. Большая форма, фильтры или корзина живут в
  соответствующем feature.
- `app/features/<feature>/` — доменная UI-логика каталога, товара, поиска,
  корзины или оформления. Создавать только нужные `components/`, `composables/`,
  `types/`, `validation/` и `services/`; использовать явные импорты из feature.
- `app/components/ui/` — недоменные primitives: кнопка, поле, бейдж, контейнер,
  диалог, состояния. `app/components/shared/` — сложные, но недоменные паттерны,
  например шапка, подвал и секционный заголовок. Shared UI не импортирует
  feature, API DTO или бизнес-store.
- `app/composables/` — общие Nuxt composables, `app/services/` — транспорт и
  mapping внешнего API, `app/utils/` — чистые функции. Общий service не зависит
  от Vue-компонента. Domain service допустим внутри feature, если не нужен другим.
- `app/layouts/` содержит shell. Header, footer и глобальные overlay не
  дублируются на страницах. `app/app.vue` остаётся корневой композицией Nuxt.
- `server/` использовать лишь для обоснованных Nuxt/Nitro задач, например
  безопасного server proxy или динамического sitemap. Не копировать в Nuxt
  бизнес-правила, хранение заказов и авторизацию Laravel.

Путь — ориентир для новых модулей, а не повод создавать пустые папки или
массово переносить существующий код. Названия файлов компонентов должны быть
однозначны с учётом Nuxt auto-import и вложенности. Для feature-компонентов
предпочтителен явный импорт; не рассчитывать на не настроенное auto-scan.

## Компоненты и читаемость

- Vue SFC пишутся через `<script setup lang="ts">` и типизированные props,
  emits, slots, API-ответы и состояния. Исключать `any`, скрытые side effects и
  логику, зависящую от конкретной страницы, в общих компонентах.
- Presentational компонент получает данные через props/slots, сообщает о
  действиях через emits и не знает endpoint, route или способ хранения данных.
  Это делает его пригодным для повторного применения на разных страницах.
- Feature-компонент может знать свою предметную область, но должен иметь
  понятный внешний интерфейс и не зависеть от структуры соседней страницы.
  Не превращать каждую секцию в универсальный компонент, если это ухудшает API.
- Сначала искать существующий primitive или shared-паттерн; расширять его
  совместимым вариантом, если внешний вид и семантика совпадают. Глобальную
  перемену вносить в primitive или token, не копировать CSS по страницам.
- Composable владеет реактивным состоянием и сценарием; service — запросом и
  преобразованием данных; компонент — разметкой и событиями. Валидация и
  форматирование цены/единицы измерения не прячутся в template.
- `useState` применять только к действительно разделяемому SSR-safe состоянию.
  Локальные формы и фильтры держать локально; состояние, которое должно
  переживать reload или иметь ссылку, согласовывать с URL/API. Не объявлять
  изменяемый `ref` на уровне модуля: на SSR он может смешать запросы пользователей.

## Nuxt, данные и API

- Использовать файловую маршрутизацию `app/pages/`, `NuxtLink` для внутренних
  ссылок, `navigateTo` для программной навигации, layouts и route middleware
  по назначению. Не добавлять ручной Vue Router вместо возможностей Nuxt.
- Индексируемые страницы получают данные при SSR через `useFetch` или
  `useAsyncData` с устойчивым ключом и обработкой `status`/`error`.
  Запросы по пользовательскому событию выполняются через service и `$fetch`.
  Не вызывать голый `$fetch` в setup для первого рендера: это ведёт к
  повторной загрузке при hydration. Не применять `ClientOnly` к основному
  содержимому каталога, категории или товара.
- Endpoint URL, заголовки, cart token, idempotency key, ошибки и transport DTO
  принадлежат service-слою. Не строить URL API и не вызывать HTTP напрямую из
  `.vue`. Не доверять цене, остаткам или итогу, вычисленным в браузере;
  серверный ответ и backend validation авторитетны для checkout.
- Публичную конфигурацию брать из `runtimeConfig.public`. Секреты существуют
  только в приватной конфигурации Nitro и никогда не попадают в HTML, payload
  или client bundle. Не передавать PII в URL, telemetry, обычные логи и
  клиентские ошибки.
- Для каждого публичного маршрута задавать подходящие `useSeoMeta`/`useHead`,
  title, description, canonical, Open Graph и structured data согласно задачам
  Phase 8/10. Использовать ЧПУ; не создавать дублирующие индексируемые URL.
  SEO-контент и метаданные должны присутствовать в SSR HTML.
- Изображения: осмысленный `alt`, объявленные размеры или aspect ratio против
  CLS, оптимизированные форматы и responsive sizes; hero/LCP грузить с высоким
  приоритетом, остальные — по потребности. `app/assets/` — обрабатываемые
  сборкой ресурсы, `public/` — файлы с постоянным публичным URL. Медиа товаров
  брать из управляемого API, не из HTML-образца.
- Писать SSR-safe код: `window`, `document`, `localStorage`, observers и таймеры
  только в client lifecycle/guard, с cleanup. Не допускать различия серверной
  и первой клиентской разметки. `useState` и async payload должны быть
  сериализуемыми.

## Дизайн, адаптивность и доступность

Визуальная реализация обязана соответствовать
[`docs/CLIENT_UI_KIT.md`](../../docs/CLIENT_UI_KIT.md). Токены размещать в
`app/assets/css/`, подключать через Nuxt; специфичные стили держать рядом с
компонентом. Не вводить произвольные цвета, шрифты, радиусы, тени или
анимации для уже описанных паттернов. Новое визуальное решение сначала
обосновать и записать в UI-kit.

Семантические ссылки и кнопки, видимый `focus-visible`, доступные названия
controls, клавиатурное управление, focus trap/возврат фокуса для dialog и
drawer, Escape, `prefers-reduced-motion`, корректные disabled/loading/error/
empty/success состояния обязательны. Важные действия не скрывать только за
hover. Узкий экран не должен иметь горизонтальный overflow.

## Порядок каждой клиентской задачи

1. Прочитать корневой `AGENTS.md`, этот файл, `docs/CLIENT_UI_KIT.md`,
   `docs/UI_DESIGN_REVIEW.md`, релевантную задачу в `tasks/`, API-контракт и
   существующий код. Сверить референс с реальным бизнес-сценарием.
2. Составить короткий план и обозначить, какие tokens, primitives, shared и
   feature-компоненты нужны. Не менять несвязанные модули.
3. Реализовать UX со всеми состояниями, SSR/SEO и accessibility. Новый общий
   паттерн включить в UI-kit; при намеренном отступлении от референса записать
   причину и получить согласование до внедрения.
4. При установленных зависимостях запустить `npx nuxt typecheck`,
   `npm run build`, релевантные тесты и доступные lint/format checks из
   `frontend/client/`. Новые скрипты добавлять
   по мере появления соответствующих инструментов; не заявлять, что
   несуществующий gate прошёл. При API-изменении обновить OpenAPI и документы.
5. Визуально проверить изменённые маршруты на ширинах 320, 640, 768, 1024 и
   1280 px. При правке tokens/layout/shared UI проверить все затронутые
   маршруты. До сдачи пройти независимый UI Design Guard по
   `docs/UI_DESIGN_REVIEW.md` и устранить blocking findings.
6. Проверить diff и статус задачи, перечислить изменённые файлы, проверки и
   оставшиеся ограничения. Не создавать commit без явного указания.

## Запрещённые сокращения пути

- вставлять `exampleSite.html` целиком, CDN Vue или его Options API в Nuxt;
- переносить demo-контент PIETRA, внешние изображения и фиктивные действия
  корзины/заказа в production;
- raw HTTP в страницах/компонентах, дублирование UI primitives и inline-стили
  для глобальных паттернов;
- `ssr: false` или `ClientOnly` для SEO-страниц ради обхода hydration-ошибок;
- использовать лишь CSS-скрытие для доступа, либо считать client validation
  достаточной для заказа и обработки ПДн;
- обновлять визуальные baseline без просмотра и подтверждения изменения.
