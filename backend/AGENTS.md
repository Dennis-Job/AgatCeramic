# AGENTS.md — правила разработки backend AgatCeramic

Этот файл обязателен для любых изменений внутри `backend/`. Он дополняет корневой
`AGENTS.md`: требования проекта, безопасности и процесса из корневого файла также
должны выполняться.

## 1. Цель

Backend — Laravel API-only приложение. Код должен быть понятен Laravel-разработчику
без знания истории проекта, легко тестироваться и изменяться локально, без скрытых
побочных эффектов.

При выборе решения приоритеты такие:

1. корректность и безопасность;
2. стандартные возможности и конвенции Laravel;
3. ясные границы ответственности;
4. простота;
5. повторное использование только там, где оно действительно нужно.

SOLID не означает создание интерфейса или отдельного слоя для каждого класса.
Абстракция должна решать существующую задачу, а не предполагаемую будущую.

## 2. Обязательный поток зависимостей

Типовой write-flow:

`Route -> Form Request -> Controller -> Service / Use Case -> Model / Repository -> DB`

Типовой read-flow:

`Route -> Form Request -> Controller -> Query / Model -> API Resource`

Допустимые направления зависимостей:

- HTTP-слой вызывает application-слой;
- application-слой использует domain/data/integration-компоненты;
- инфраструктурные адаптеры реализуют потребности application-слоя;
- Job/Command/Listener является входным адаптером и вызывает use case или service;
- API Resource отвечает только за публичное представление данных.

Запрещены обратные зависимости: service не должен знать о Controller, Request,
Resource или HTTP response; Model не должен разрешать и вызывать application services.

## 3. HTTP-слой

### Routes

- API версионируется и сохраняет разделение public/admin routes.
- Используются resource routes и стандартные HTTP verbs, когда они подходят.
- Изменение маршрута или payload одновременно отражается в OpenAPI.
- В route closure не размещается бизнес-логика.

### Form Requests

- Для нетривиальной validation/authorization/normalization используется отдельный
  Form Request.
- Controller и service получают только проверенные данные; нельзя передавать туда
  без разбора `$request->all()` или непроверенный input.
- Нормализация входа выполняется в Form Request, DTO/factory или специализированном
  mapper, но не смешивается с сохранением данных.
- Бизнес-инварианты, зависящие от состояния системы или блокировок, проверяются в
  application-слое, а не только validator-правилами.

### Controllers

Controller должен:

1. принять типизированный Request/Form Request;
2. выполнить authorization, если её не выполнил Form Request;
3. передать валидированные данные в один use case/service/query;
4. вернуть API Resource, response или корректный status code.

В Controller запрещены:

- транзакции и блокировки;
- изменение Eloquent-моделей и массовая orchestration нескольких записей;
- SQL/DB facade;
- сложные фильтры, условные query chains и обогащение справочниками;
- работа с файлами, очередями и внешними API;
- service locator через `app()`/`resolve()`;
- глобальные `request()` и `auth()`, когда зависимость можно принять явно.

Простой однострочный CRUD/read query допустим. Если query содержит несколько
условий, повторяется, формирует отдельную проекцию или подмешивает справочные данные,
он выносится в Query object.

### API Resources

- Публичные API не возвращают Eloquent Model напрямую.
- Форматирование, условные поля и вложенные представления находятся в Resource.
- Resource не выполняет запросы, бизнес-решения или mutation.
- Нужные relations загружаются до создания Resource; N+1 не маскируется внутри него.

## 4. Application services и use cases

- Один публичный метод должен представлять один законченный сценарий.
- Зависимости передаются явно через constructor или method injection.
- `app()`/`resolve()` внутри production-кода запрещены, кроме Laravel callback, в
  который framework объективно не может внедрить зависимость. Исключение должно
  иметь короткий комментарий с причиной и отдельный тест.
- Нельзя делать dependency nullable только для удобства теста и затем разрешать её
  из container. Тест вызывает production API так же, как приложение.
- Service не принимает HTTP Request и не возвращает HTTP Response/Resource.
- Граница транзакции находится в use case/service, владеющем изменением данных.
- Внешние события и jobs dispatch-ятся после commit, если потребителю нужны
  сохранённые данные.
- Ошибки предметной области выражаются специализированными exceptions/result types,
  а не строками, зависящими от UI.

Класс требует обязательного review на разделение, если он:

- совмещает чтение файла, parsing, validation, planning, запись и отчётность;
- обслуживает несколько независимых workflows;
- имеет constructor с большим количеством разнородных зависимостей;
- стал больше примерно 250 строк или содержит методы больше примерно 40 строк.

Размер — сигнал для review, а не самостоятельное основание создавать бессмысленные
слои. После разделения имена компонентов должны описывать роль: reader, parser,
validator, planner, executor, exporter, report builder и т. п.

## 5. Доступ к данным

- Простой локальный Eloquent query допустим в service или небольшом Controller read-flow.
- Сложные/переиспользуемые выборки размещаются в `app/Queries/` и не изменяют данные.
- Repository вводится только при реальной необходимости изолировать persistence,
  объединить несколько источников данных или обеспечить значимую domain boundary.
  Repository/interface не создаётся только ради соблюдения схемы слоёв.
- Eloquent Model содержит relations, casts, scopes и локальное поведение сущности,
  но не workflow, внешние интеграции и container resolution.
- Для предотвращения race conditions используются DB constraints, transactions,
  atomic updates и `lockForUpdate()` там, где это обосновано.
- Денежные и точные величины не вычисляются через двоичный `float`, если ошибка
  округления влияет на данные; формат хранения и API должен быть единообразным.

## 6. PostgreSQL и migrations

- PostgreSQL является целевой СУБД; SQLite-тесты не считаются достаточным
  доказательством совместимости SQL и migrations.
- Инварианты закрепляются подходящими foreign keys, unique/check constraints и
  indexes, а не только application validation.
- Migration должна быть безопасна для существующих данных и иметь предсказуемый
  rollback либо документированное обоснование, почему rollback невозможен.
- Destructive/data migrations требуют отдельной задачи, backup/rollback-плана и
  проверки на копии данных.
- Новая выборка проверяется на N+1 и наличие индексов для основных фильтров/sort.

## 7. Очереди, файлы и интеграции

- Job передаёт идентификаторы и небольшой сериализуемый контекст, а не большие
  object graphs и чувствительные payloads.
- Job должна быть идемпотентной либо иметь явную защиту от повторного выполнения.
- Для Job явно определяются `tries`, `backoff`, `timeout` и failure cleanup, когда
  операция не мгновенная.
- Временные файлы имеют владельца жизненного цикла и гарантированно очищаются после
  success/failure/expiry.
- Интеграция изолируется adapter/client-классом; transport details не протекают в
  Controller и domain logic.
- Секреты читаются через config; прямой `env()` вне config-файлов запрещён.

## 8. Authorization, PII и журналирование

- Доступ к admin-функциям защищается middleware и Policy/Gate; UI-проверка не
  является контролем доступа.
- Новое permission выдаётся минимально необходимым ролям и покрывается отрицательным
  тестом.
- В обычные application logs, exceptions, analytics и queue payloads не попадают
  ФИО, телефон, адрес, email, токены, cookies и другие чувствительные данные.
- Для диагностики используются технические IDs, correlation ID и маскирование.
- Доступ к PII, export и административным изменениям должен попадать в audit trail,
  если это предусмотрено моделью угроз и политикой хранения.

## 9. Стиль и читаемость

- Код проходит Laravel Pint и PHPStan на настроенном проектом уровне.
- Для параметров, properties и return values используются точные типы. Необъяснимый
  `mixed` и массивы неизвестной формы запрещены; сложная форма описывается DTO,
  value object, enum или PHPDoc array shape.
- Имена классов и методов отражают действие или роль, а не технические слова вроде
  `Manager`, `Helper`, `Common`, если более точное имя возможно.
- Метод выполняет действие на одном уровне абстракции; happy path читается сверху вниз.
- Early return предпочтительнее глубокой вложенности.
- Комментарий объясняет причину, ограничение или компромисс, но не пересказывает код.
- Не допускаются закомментированный код, неиспользуемые зависимости и suppressions
  без причины.
- Новые module namespaces/folders вводятся целиком в рамках отдельной задачи; нельзя
  частично перемещать существующий модуль и оставлять две конкурирующие структуры.

## 10. Тесты

- Тестируется наблюдаемое поведение и контракт, а не private implementation details.
- Production-сигнатуры нельзя усложнять ради прямого вызова из старого теста.
- Для каждого изменения проверяются happy path, validation, authorization и важные
  failure/race/idempotency paths.
- Queue fake подходит для проверки dispatch; реальный worker нужен для критичного
  end-to-end queue flow.
- DB-зависимые функции проходят PostgreSQL feature/integration suite.
- Исправление дефекта начинается с regression test, когда это практически возможно.

## 11. Definition of Done

Для backend-изменения перед сдачей должны быть выполнены релевантные проверки:

```bash
composer validate --strict
composer audit --locked
vendor/bin/pint --test
composer analyse
composer test
```

Дополнительно необходимо:

- проверить migrations на PostgreSQL, если меняется DB/schema/query behavior;
- обновить OpenAPI при изменении API;
- обновить документацию и статус задачи;
- проверить `git diff` и список изменённых файлов;
- перечислить запущенные проверки и честно указать непройденные/не запущенные;
- не создавать commit без прямого запроса пользователя.

## 12. Checklist review

Перед завершением ответить «да» на вопросы:

- Controller остался тонким и не скрывает business/query orchestration?
- Все зависимости видны из сигнатур?
- Validation, authorization и serialization находятся в правильных слоях?
- Новая абстракция действительно уменьшает связанность или дублирование?
- Транзакция, concurrency и повторный запуск обработаны безопасно?
- API/OpenAPI и error contract не разошлись?
- PII/секреты отсутствуют в logs, payloads и test fixtures?
- Код понятен без устного объяснения автора?
- Тесты проверяют контракт и негативные сценарии?
